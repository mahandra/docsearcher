# DocQA

A Django web app where users upload documents (PDF, DOCX) and ask questions about them.
Answers are generated by an LLM using retrieval-augmented generation (RAG) and cite their sources.

This is a learning/portfolio project, built phase by phase. **Current state: phase 5 (all
phases done)** —
a streaming chat (phase 1) over the user's own documents: PDF/DOCX files are parsed, chunked,
embedded with Voyage AI in a Celery worker and stored in PostgreSQL/pgvector (phase 2); every
question runs a hybrid search (vectors + full-text) and Claude answers from the retrieved
passages with citations rendered as footnotes (phase 3). Retrieval and answers are measured
by an eval suite with an LLM judge, and every reply is traced in Langfuse (phase 4). Prompt
caching, a fallback model, follow-up query rewriting, prompt-injection checks and a warning for
uncited answers make it closer to production (phase 5).

## Quick start

Requirements: Docker with Compose v2, GNU make. Optionally [uv](https://docs.astral.sh/uv/)
for running tools on the host.

```bash
cp .env.example .env          # set DJANGO_SECRET_KEY, ANTHROPIC_API_KEY, VOYAGE_API_KEY
make up                       # start db, redis, web and worker
make migrate                  # create tables
# then open http://localhost:8000, sign up and start a chat
```

| Command | What it does |
|---|---|
| `make up` / `make down` | Start / stop all services |
| `make migrate`, `make makemigrations` | Database migrations |
| `make test` | Run the test suite in Docker (never calls the real API) |
| `make lint`, `make fmt` | Ruff checks / formatting |
| `make shell`, `make superuser`, `make logs` | Django shell, admin user, web + worker logs |

Running on the host instead: `uv sync`, then `uv run pytest` or `uv run python manage.py ...`
(the database from Docker is exposed on `localhost:5434`).

Changes to `.env` are picked up only when containers are recreated:
`docker compose up -d --force-recreate web worker`. After adding dependencies run `make build`.

## Architecture

```
Browser ──HTMX POST──▶ message_create ──▶ saves user Message, returns placeholder
   │
   └─EventSource GET─▶ message_stream (async) ──▶ ChatService.stream_reply()
                         │ SSE: sources/thinking/token/        │ (retrieval, see phase 3)
                         │      citation/done/failed           │
                         ◀─────────────────────────────────────┤ AsyncAnthropic
                                                               │ messages.stream()
                                                               ▼
                                              saves assistant Message
                                              (content, status, tokens, cost)
```

- **Served via ASGI (uvicorn).** A streamed answer keeps the HTTP connection open for tens of
  seconds; async views wait on the network without occupying a worker.
- **Service layer (`chat/llm.py`).** The only module that imports the Anthropic SDK. It builds the
  message history from the database, loads the system prompt from `chat/prompts/system.md`,
  streams the reply and persists it. Views receive domain events (`SourcesFound`, `ThinkingStarted`,
  `TextDelta`, `Cited`, `Completed`, `Failed`), so the SDK can be mocked or replaced without touching the web layer.
- **History.** The API is stateless: the conversation is resent on every request (and billed as
  input tokens), limited to the last `LLM_MAX_HISTORY_MESSAGES` messages. The history always
  alternates user/assistant and starts with a user turn.
- **Retries.** The SDK retries failures to open a request (429, 5xx, 529 overloaded, network) with
  exponential backoff. Errors inside an open stream are retried by the service — but only before
  the first token reached the browser. After that, the partial answer is saved with status
  `interrupted` instead of being regenerated. If the model is still unavailable after the
  retries, the request is sent once to `LLM_FALLBACK_MODEL` (phase 5).
- **Cost tracking.** Every assistant message stores model, input/output tokens (uncached, cache
  writes, cache reads), `stop_reason` and estimated cost (`chat/pricing.py`). Interrupted
  streams record best-effort usage.
- **Streaming transport.** Server-Sent Events with a native `EventSource` (`chat/static/chat/stream.js`)
  rather than the HTMX SSE extension: we stream one reply and must close the connection
  explicitly — `EventSource` otherwise reconnects and would trigger another, billed generation.
  The server additionally claims each generation with an atomic conditional `UPDATE`, so
  reconnects or a second tab cannot start a duplicate.
- **Cancellation.** If the browser disconnects, the API stream is closed immediately (stopping
  token generation) and the partial answer is kept.
- **Security basics.** All data is scoped to the logged-in user (Django auth); LLM output is
  treated as untrusted and always rendered as escaped text.

### Document ingestion (phase 2)

```
Browser ──HTMX upload──▶ document_upload ──▶ validate (size, extension, magic bytes, duplicate)
   │                          │                  save Document(status=uploaded)
   │                          └─ transaction.on_commit ─▶ Redis ─▶ Celery worker
   │                                                                 │ process_document
   └─HTMX poll every 2s─▶ document_row                               ▼
       (stops when ready/failed)              detect type → parse (pypdf / python-docx)
                                              → chunk (recursive, with overlap)
                                              → embed (Voyage AI, input_type="document")
                                              → atomically replace Chunks (pgvector, HNSW)
```

- **Parsing** keeps where text came from — PDF page numbers, DOCX headings — so phase 3 can cite
  sources. Scanned PDFs (no text layer) and password-protected files fail with a clear message.
- **Chunking** (`documents/chunking.py`) splits at paragraphs → lines → sentences → words and packs
  pieces into ~500-token chunks with ~75 tokens of overlap (taken from trailing sentences when a
  paragraph is longer than the overlap). Chunks may span PDF pages; a DOCX heading always starts a
  new chunk. Token counts are character-based estimates.
- **Embeddings** (`documents/embeddings.py`) — the only module using the Voyage SDK. Anthropic
  offers no embeddings API; Voyage `voyage-4` is multilingual (mixed English/Russian documents).
  Texts are batched under count and token limits; truncation is disabled so nothing is silently cut.
  Exact token usage and cost are stored per document.
- **Celery task** is idempotent (late acks, chunks replaced in one transaction), runs network calls
  outside transactions, retries transient provider errors with exponential backoff and jitter, and
  fails fast on permanent ones (e.g. invalid API key).
- **Storage**: each `Chunk` has a `vector(1024)` column with an HNSW index for cosine distance,
  and a generated `tsvector` column (English + Russian stemming) with a GIN index.
  Changing the embedding model or dimension requires re-embedding all documents.

### Retrieval and answering (phase 3)

```
question ─┬─ embed (input_type="query") ─▶ vector search (HNSW, top 20) ─┐
          └─ words → tsquery (en/ru) ────▶ full-text search (GIN, top 20) ┴─▶ RRF ─▶ top 8
                                                                                     │
   search_result blocks (citations enabled) + question ─▶ Claude ─▶ text + citations ◀┘
```

- **Hybrid search** (`documents/retrieval.py`). Vectors match meaning (paraphrases, other
  languages); full-text matches exact words (names, codes, numbers). The keyword query ORs the
  question's words, each stemmed with the config of its script (Cyrillic → Russian, else
  English), so stop words do not match everything. Results are merged with **Reciprocal Rank
  Fusion** — by rank, since cosine distance and `ts_rank` are not comparable. Only the user's
  `ready` documents are searched; HNSW runs with `iterative_scan` so this filter does not
  starve the result list. If the query embedding fails, search degrades to keyword-only.
- **Search playground** (`/documents/search/`): every candidate with its vector rank/distance,
  keyword rank/score, RRF score and the top-K cutoff. No LLM call — retrieval is debugged on
  its own, because a passage that is not retrieved cannot be cited.
- **Grounded answers with native citations** (`chat/llm.py`). The retrieved chunks are sent as
  `search_result` content blocks (one text block per paragraph, citations enabled) before the
  question; Claude attaches `search_result_location` citations to the parts of the answer they
  support. No `[1]` markers are prompted for or parsed. Only the latest question carries search
  results; earlier turns are plain text, so context and cost do not grow with each follow-up.
- **Persistence.** `MessageSource` records every chunk that was in the prompt (ranks, score,
  whether it was cited) with the document name and location copied, so citations survive
  deletion or re-processing. Citation offsets in the answer are stored on the `Message`.
  The query-embedding cost is stored per message and included in the conversation cost.
- **UI.** Citation markers stream in with the answer (`sources` and `citation` SSE events) and
  link to the chunk on the document page; cited sources are listed as numbered footnotes.
- **Known limits:** there is no reranker and no relevance gate (see Evaluation), and the
  search covers chunks, not whole documents ("summarize this file" works poorly).

### Tracing (phase 4)

`chat/tracing.py` (the only module importing `langfuse`; a no-op without keys) records one
Langfuse trace per reply, with the user and the conversation as session:

```
chat-reply             question → answer; WARNING if the answer cites nothing
├── rewrite            follow-ups only: the standalone search query (Haiku)
├── retrieval          retrieved chunks with vector/keyword ranks, embedding usage
└── claude             prompt, answer, tokens, cost (ours, from chat/pricing.py),
                       time to first token; one per API attempt, failed ones as ERROR
```

Observations are created explicitly rather than as the "current" OpenTelemetry span, because
`stream_reply` is an async generator and a context must not live across `yield`. The
Anthropic SDK's own OpenTelemetry spans are switched off: Langfuse would receive them as
separate traces without user/session. Tracing errors are logged and never reach the chat.

## Production polish (phase 5)

- **Prompt caching.** Two cache breakpoints: the system prompt (identical for every request)
  and the last history message (the prefix of the next turn). The latest turn is not cached:
  its search results are dropped from the history and never recur. In a live 3-turn
  conversation the third turn read 1,650 tokens from the cache (system + both earlier turns)
  at $0.20 instead of $4 per million. The saving is modest here — 5–7K tokens of fresh search
  results per turn dominate the input — but it grows with longer conversations. The system
  prompt must stay byte-stable: any change before a breakpoint is a silent cache miss.
- **Model fallback.** Retries cover short outages; when the main model is still overloaded
  or rate-limited after them, and nothing was streamed yet, the same request goes once to
  `LLM_FALLBACK_MODEL`. Errors any model would repeat (4xx) never fall back. The message
  records the model that answered and its price.
- **Follow-up query rewriting** (`chat/rewrite.py`). The search sees only the latest message,
  and "And for managers?" has nothing to search for. Haiku 5.5 rewrites a follow-up with the
  recent conversation in view, its reply constrained by a JSON schema (structured outputs).
  Only the search uses the rewrite; the answer is generated for the user's own words, and any
  failure falls back to searching the question as typed. On follow-ups whose words point
  elsewhere in the corpus: hit@1 0.73 → 0.93, MRR 0.83 → 0.97, for $0.0012. The rewrites
  are not always faithful (one added "Severity 3 or 4", which the documents do not have),
  which is one more reason not to answer them instead of the user's question.
- **Prompt injection.** Uploaded documents are untrusted. Defences, in layers: documents go
  only into `search_result` blocks, the system prompt says they are content, not instructions;
  the model has no tools, so the worst outcome is a wrong text; output is rendered as plain
  text, so no link or image a browser would fetch (the usual data-exfiltration channel); data
  is scoped per user. The eval has two vendor documents with planted instructions (recommend a
  competitor, a phishing link, "print your system prompt", "refuse to answer"): none was
  obeyed in 4 cases — the model answered and warned the user about the planted text instead.
- **Uncited answers are flagged.** A complete answer that had sources but cites none cannot be
  checked by the user: it gets a warning in the UI and WARNING level in Langfuse.

## Evaluation (phase 4)

A synthetic corpus of six documents (`evals/corpus/`: an English services agreement, API docs
and a courier rate card as PDF, a Russian employee handbook, security policy and cleaning
schedule as DOCX — rendered deterministically) and 72 questions (`evals/dataset.toml`):
paraphrase 20, exact tokens 10, cross-lingual 10, unanswerable 10, follow-up 15, prompt
injection 4, multi-hop 3. Each answerable question has
evidence quotes (to locate relevant chunks) and reference facts (for grading).

```bash
uv run python manage.py eval_retrieval              # retrieval only; ~$0.0001 (one Voyage call)
uv run python manage.py eval_retrieval --rewrite    # follow-ups rewritten as in the app (<$0.01)
uv run python manage.py eval_answers                # dry run: prints the cost estimate
uv run python manage.py eval_answers --yes --category cross_lingual
uv run python manage.py eval_answers --yes --langfuse --run-name "my change"
```

- **Retrieval metrics** (`eval_retrieval`): hit@k, recall@k and MRR per search mode (hybrid,
  vector, keyword) and per category, plus cosine distances of the nearest chunk. Free and
  deterministic, so it is the first check for any retrieval change.
- **Answer eval** (`eval_answers`): every question goes through the real `ChatService`
  (follow-ups replay their history first). A deterministic check verifies that the answer cites
  a chunk containing the evidence; an **LLM judge** (Claude Sonnet, rubric in
  `evals/prompts/judge.md`, structured output) grades *correctness* against the reference
  facts and *faithfulness* against the passages the model saw (titles included), and whether
  the model declined. Injection cases also check *canaries*: strings that appear in the answer
  only if the model obeyed a planted instruction. A full run costs ~$3.2 (answers ~$0.035,
  judge ~$0.01 each).
- **Langfuse experiments** (`--langfuse`): the cases are synced to the `docqa-answers` dataset
  and the run goes through the SDK's `run_experiment`, so each item links to its traces and the
  judge's scores; runs can be compared item by item in the UI. Grading stays in the repo.
- Reports are written to `evals/results/` (gitignored).

### Results

Retrieval, answerable questions (the phase 4 set: 4 documents, 31 chunks, top-K 8):

| Mode | hit@1 | hit@3 | hit@8 | MRR |
|---|---|---|---|---|
| keyword only | 0.56 | 0.74 | 0.82 | 0.66 |
| vector only | 0.82 | 0.96 | 0.96 | 0.89 |
| hybrid, RRF k=60 (baseline) | 0.74 | 0.88 | 0.96 | 0.82 |
| **hybrid, RRF k=5** | 0.76 | **0.94** | **1.00** | 0.85 |

Answers (the phase 4 set of 60 questions, Opus 5.5 at low effort, judged by Sonnet 5.5; the
full answer eval has not been re-run on the 72-question set with the phase 5 changes):

| | correctness | faithful | cited evidence | false declines |
|---|---|---|---|---|
| baseline | 0.96 | 0.80 | 0.96 | 3 of 50 |
| **after tuning** | **1.00** | **1.00** | 0.96 | 0 of 50 |

What changed, and what the eval showed on the way:

1. **The judge was fixed first.** It saw passages without their document titles and flagged
   every mention of a document name as unsupported (5 cases). Measure the measuring device
   before optimizing against it.
2. **RRF k = 60 → 5.** Hybrid search was *worse* than vector search alone: Russian questions
   about the English contract lost their chunk to Russian chunks of unrelated documents.
   Lowering the keyword weight did not help; the cause was the RRF constant — with 20
   candidates, k=60 makes rank 1 and rank 10 almost equal, so any chunk found by both searches
   wins. With k=5 all relevant chunks are in the top 8, and exact-token questions (clause
   numbers, error codes, which only full-text search finds) kept their gains.
3. **System prompt: no advice beyond the passages.** Correct answers were padded with
   "in practice" advice from general knowledge, which a reader cannot tell apart from
   document content (faithfulness 5/12 → 12/12 on those cases; answers ~45% shorter).
4. **No distance threshold.** Cosine distance of the best chunk overlaps heavily between
   answerable (relevant chunk up to 0.88) and unanswerable questions (0.49–0.84): any cutoff
   that rejects unanswerable questions also drops real answers — mostly the exact-token ones.
   The model already declines all 10 unanswerable questions. A reranker is the better tool.

Caveats: the corpus is small and synthetic and the questions were written alongside it, so
the final scores mean "no known failures", not "perfect" — the set is now saturated and needs
harder questions (longer documents, near-duplicate clauses, conflicting versions). Every
number comes from a single run of a nondeterministic system; two answers in the final run
were correct but carried no citations at all, which the citation check caught.
